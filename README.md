# sellgar.shop.service

Источник истины для сведений о магазине. Каталог, цены, остатки, резервы, фискализация и заказы
этому сервису не принадлежат.

## Модель

- `shop` — магазин и продавец: название и юридические реквизиты;
- `shop_contact` — публичные и служебные контакты по назначению;
- `shop_address` — адреса претензий, возвратов и пунктов выдачи;
- `outbox_event` — события, записанные в транзакции вместе с агрегатом.

## RMQ-контракт

- `shop.getAll`, `shop.getByUuid`;
- `shop.create`, `shop.update`;

Изменяемые агрегаты используют optimistic version.

При чтении карточки контакты упорядочены по `sortOrder`, адреса — по позиции в массиве
`addresses`, переданном при создании или обновлении. Сервис сохраняет позиции адресов
в `shop_address.sort_order`. Изменение назначения контакта или типа адреса не меняет его позицию.

## Поиск магазинов

`shop.getAll` принимает необязательный `term` вместе с `limit` и `offset`. Поиск выполняется
в PostgreSQL по названию магазина, наименованию организации, ФИО ИП и реквизитам
`inn`, `kpp`, `ogrn`, `ogrnip`. Каждое слово запроса должно совпасть с началом слова
или его русской словоформой: `про` находит «Проверка», `Sel` — «Sellgar»,
`проверку рекв` — «Проверка реквизитов». Часть ИНН или ОГРН ищется с начала номера.
Словарь `simple` сохраняет короткие слова, которые `russian` может отбросить;
словарь `russian` обеспечивает совпадение словоформ. Пунктуация разделяет слова;
специальный синтаксис поисковых операторов не используется.
Пустой или пробельный `term` возвращает обычный список. `meta.totalRows` учитывает фильтр.

Миграция `AddShopFullTextSearch1791630000000` создаёт GIN-индекс выражения,
а `EnableShopPrefixSearch1791633600000` заменяет его индексом объединённого вектора
`simple` и `russian`. PostgreSQL
поддерживает его при изменении исходных полей; отдельная синхронизация не нужна.

Проверка на локальной PostgreSQL, после `yarn migration:run`:

```bash
SHOP_SEARCH_INTEGRATION=true yarn test --runInBand shop.repository.integration.spec.ts
```

Проверочные записи поиска создаются в транзакции и откатываются после тестов. Тест сохранения
адресов создаёт временный магазин через репозиторий и удаляет его после проверки. Без переменной
`SHOP_SEARCH_INTEGRATION=true` тесты, которым нужна БД, пропускаются.

## Юридические сведения

Поддерживаются только российская организация (`legal_entity`) и ИП
(`individual_entrepreneur`). Это тип продавца, а не режим налогообложения.

| Поле                    | Организация          | ИП                                               |
| ----------------------- | -------------------- | ------------------------------------------------ |
| `legalName`             | обязательно          | запрещено                                        |
| `entrepreneurFullName`  | запрещено            | обязательно; отчество при наличии                |
| `inn`                   | 10 цифр              | 12 цифр                                          |
| `kpp`                   | обязательно, 9 цифр  | запрещено                                        |
| `ogrn`                  | обязательно, 13 цифр | запрещено                                        |
| `ogrnip`                | запрещено            | обязательно, 15 цифр                             |
| `registrationAuthority` | запрещено            | обязательно, наименование регистрирующего органа |
| `legalAddress`          | юридический адрес    | адрес регистрации                                |
| `email`, `phone`        | минимум один контакт | минимум один контакт                             |

`legalDetails` заменяется целиком; при изменении типа клиента поля прежнего типа передаются
как `null` или отсутствуют. Переданные неприменимые значения сервис отклоняет. Частичное
обновление внутри `legalDetails` не поддерживается. Отсутствие `legalDetails` в `shop.update`
сохраняет существующие реквизиты. Старая возможность записи магазина без юридического блока
сохранена; административная форма требует заполнения реквизитов.

Состав реквизитов проверяется `class-validator` на DTO и командах. PostgreSQL CHECK защищает
ветви от смешивания и пропущенных обязательных полей, включая SQL NULL. Проверяются форматы
номеров; проверка контрольных цифр и существования записи в реестре ФНС не реализована.
Миграция `ValidateShopLegalDetails1791522000000` проверяет существующие записи: при несовместимых
данных откатывается, реквизиты автоматически не заполняет и не очищает.

### Основания для публичных сведений

Проверено 05.10.2026. Набор полей учётной системы не равен перечню обязательной публикации.

- Пункт 19 Правил № 2463: организация публикует наименование, ОГРН, адрес и место нахождения,
  email и/или телефон; ИП — ФИО (отчество при наличии), ОГРНИП, email и/или телефон.
  [Роспотребнадзор](https://zpp.rospotrebnadzor.ru/info/analysis/337586).
- Статья 9 Закона № 2300-1: сведения о государственной регистрации ИП и зарегистрировавшем
  его органе; также информация о режиме работы, а для лицензируемой деятельности — о лицензии.
  [Роспотребнадзор](https://04.rospotrebnadzor.ru/index.php/consumer-information/faq/16766-09062022.html).
- Формат ИНН: 10 цифр для организации, 12 для физического лица, включая ИП.
  [ФНС](https://www.nalog.gov.ru/rn77/terms/7756931/).

Обязательность ИНН, КПП и адреса регистрации ИП в нашей форме — контракт хранения реквизитов,
а не утверждение об обязательной публикации этих полей по пункту 19. Режим работы, сведения
о лицензии и остальные требования к конкретной витрине требуют собственного размещения;
эта модель не является проверкой полного юридического соответствия интернет-магазина.
